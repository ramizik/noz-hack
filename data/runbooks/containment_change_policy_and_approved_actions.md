# Containment Change Policy and Approved Autonomous Actions

Document owner: Security Governance and Network Security
Last reviewed: 2026-05-02
Classification: Internal Use Only

## Purpose

This policy defines which incident containment actions can be proposed or executed during a suspected cyber incident. It is written for both human responders and always-on agents. The policy enables fast, safe action without creating unnecessary business risk. It is especially relevant when SentinelOps proposes actions such as isolating `prod-db-01`, blocking `185.220.101.45`, requesting egress logs, or notifying the Security Lead.

## Guiding Principles

Preserve evidence before destructive action. Prefer narrow controls before broad outages. Keep security telemetry reachable. Record every action with owner, timestamp, reason, and rollback requirement. During a High or Critical incident, containment speed matters more than normal change windows, but responders must still document the change.

## Approved Autonomous Proposals

An agent may propose these actions without human approval:

- Request firewall logs for a specific source, destination, and time window.
- Request VPC flow logs for an affected host.
- Request EDR process timeline for an affected host.
- Request database audit logs for a suspicious table or service account.
- Draft a Security Lead notification.
- Draft a stakeholder update.
- Search Nia for runbooks, topology, asset profile, postmortems, and escalation policy.
- Create incident tasks for investigation, containment, and communications.

## Approved Emergency Actions

The following actions may be executed immediately during a High or Critical incident if the evidence matches policy criteria. In the demo system these actions are simulated but should be described exactly as production-safe controls.

Block destination IP at egress:

- Criteria: destination is unapproved and traffic originates from production, or destination appears in threat intelligence, or destination is part of the active suspicious session.
- Example: block `185.220.101.45/32` or `203.0.113.42/32` at `fw-egress-01`.
- Required note: include source host, destination, port, reason, incident ID, and rollback owner.

Apply database quarantine group:

- Criteria: restricted database host has unapproved outbound traffic, bulk export process, suspicious credential use, or confirmed access to restricted tables.
- Example: apply `sg-quarantine-db` to `prod-db-01`.
- Required note: keep EDR, telemetry, and forensic collection paths open.

Disable compromised credential:

- Criteria: evidence shows credential misuse, impossible travel, unauthorized service account use, or confirmed malicious process run by that account.
- Example: disable `svc_reporting_temp` if it runs `pg_dump` outside approved jobs.
- Required note: preserve token and session evidence first if possible.

## Actions Requiring Incident Commander Approval

These actions require approval from the Incident Commander or Security Lead:

- Shutting down a production database host.
- Restarting database services.
- Deleting files from an affected host.
- Reimaging a host.
- Blocking an entire production subnet.
- Revoking all database credentials for a business unit.
- Public customer communications.
- Declaring a breach.

For `prod-db-01`, do not shut down or restart the host during the first response cycle. Quarantine and destination blocking are preferred.

## Documentation Requirements

Every containment action must include:

- Incident ID.
- Cycle number if generated by SentinelOps.
- Proposed by: investigation, containment, communications, or escalation agent.
- Grounding source from Nia.
- Affected system.
- Action type.
- Exact target.
- Status: proposed, executing, completed, failed, or rolled back.
- Evidence that justified the action.
- Time performed.
- Rollback owner.

Example action ledger entry:

`cycle=1 proposed_by=containment action=isolate_host target=prod-db-01 status=completed grounded_source=Containment Change Policy and Approved Autonomous Actions reason="restricted database host initiated unapproved public egress"`

## Rollback Guidance

Do not roll back containment until the Incident Commander approves and the investigation lead confirms the threat path is closed. For database exfiltration, rollback requires:

- Suspicious destination blocked or proven benign.
- No active malicious process.
- Credentials reviewed.
- Table access understood.
- Legal and Security Lead agree on severity.
- Monitoring coverage active for at least one additional cycle.

## Agent Instruction

When an alert involves `prod-db-01` and unapproved outbound traffic, the agent should create a containment task and action ledger entry. The action should cite this policy, the database exfiltration playbook, and the network topology. If the second cycle confirms 2 GB transferred, add an escalation action and cite the incident command directory.
